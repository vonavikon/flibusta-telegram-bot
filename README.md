# flibusta-telegram-bot

**RU** · [EN](README.en.md) · [中文](README.zh.md) · [Español](README.es.md) · [Français](README.fr.md)
[![VirusTotal](https://img.shields.io/badge/VirusTotal-0%2F75_clean-brightgreen)](https://www.virustotal.com/gui/file/ec9224ec99c3adfa548d41b6c5fe4f53535d39a16615f7f67ece08fa62f77ce4)


Telegram-бот для поиска и скачивания книг с [Flibusta](https://flibusta.is).

LLM делает здесь одну вещь: разбирает свободный запрос в структуру «автор + название», чтобы OPDS-поиск Flibusta попадал точно. Поиск, ранжирование и скачивание детерминированы и идут без LLM. Параллельно с LLM-разбором работает детерминированный перебор - оба пула кандидатов сливаются, и книга идёт в выдачу с лучшей из двух оценок.

## Возможности

- Поиск свободным текстом («конан дойл шерлок», «блый клык лондон»): LLM вытаскивает автора и название, перебор разбиений страхует параллельно.
- Ранжированный список с форматами, размером, числом скачиваний и переводчиком; 3 страницы по 5 книг.
- Карточка книги с описанием и кнопками форматов (fb2, epub, mobi, pdf, txt, rtf, html).
- Скачивание с распаковкой: Flibusta отдаёт текстовые форматы в zip, бот достаёт внутренний файл, чтобы читалка его открыла.
- Стриминг хода поиска в чат: «разбираю», «ищу», «листаю страницу 3/10», «сравниваю». Пользователь видит, что бот делает, а не ждёт в тишине.
- Дневные лимиты на скользящем окне 24 ч: 10 скачиваний, 50 поисков, плюс список безлимитных ID.
- Аналитика в SQLite (`/stats`), кэш поиска в памяти на 6 часов.
- Лог запросов и выбранных книг в JSONL (telegram id хешируется sha256) - для собственной аналитики качества поиска.

## Как используется LLM

На каждый некэшированный поиск - один вызов `parseQuery`, который переводит текст в `{authors, title, series, genre}`. Дальше LLM не участвует.

Поиск идёт двумя путями одновременно:

1. **LLM-разбор** - структура из `parseQuery` идёт в OPDS-поиск Flibusta по автору и названию.
2. **Детерминированный перебор** (`splitSearchBooks`) - запрос дробится на варианты «автор + название» и каждый проверяется поиском, без LLM.

Пулы кандидатов сливаются, каждая книга оценивается по обоим разборам и берётся максимум. Перебор покрывает случаи, где LLM промахивается (поиск только по автору, грязные реальные запросы), и страхует при падении провайдера: если LLM недоступен, поиск уходит в degraded (запрос целиком как название), а перебор всё равно отрабатывает. Reasoning у LLM выключен ради скорости; кэшированные запросы не делают ни одного вызова.

Замер на 200 запросах (100 книг, каждая чистой и грязной формулировкой): объединение LLM и перебора даёт 80% точных попаданий в топ-3 на чистых и 75% на грязных; без LLM поиск грязных запросов проваливается до 17% - перебор не умеет вытаскивать автора и название из фразы с опечаткой и мусором.

## Требования

- Node 20 (проще всего через Docker).
- Токен бота Telegram от @BotFather.
- API-ключ OpenAI-совместимого LLM-провайдера (bothub.chat, OpenAI и др.).
- Сервер или VPS с Docker.

## Конфигурация

```bash
cp .env.example .env
```

| Переменная | Обяз. | По умолч. | Описание |
|---|---|---|---|
| `BOT_TOKEN` | да | - | токен @BotFather |
| `ADMIN_IDS` | да | - | Telegram ID админов через запятую, видят `/stats` |
| `LLM_API_KEY` | да | - | ключ LLM-провайдера |
| `LLM_BASE` | да | - | OpenAI-совместимый эндпоинт, напр. `https://openai.bothub.chat/v1` |
| `MODEL` | да | - | модель, напр. `gemini-2.5-flash` |
| `FLIBUSTA_BASE` | да | - | зеркало Flibusta, напр. `https://flibusta.is` |
| `FLIBUSTA_FALLBACK_BASE` | нет | - | запасное зеркало |
| `ALLOWED_IDS` | нет | (пусто) | whitelist; пусто - бот публичный |
| `UNLIMITED_IDS` | нет | - | ID без дневных лимитов |
| `DOWNLOAD_DAILY_LIMIT` | нет | 10 | скачиваний за 24 ч |
| `SEARCH_DAILY_LIMIT` | нет | 50 | поисков за 24 ч |
| `RATE_LIMIT_PER_MIN` | нет | 20 | запросов в минуту на пользователя |
| `MAX_QUERY_LEN` | нет | 100 | максимальная длина запроса, символов |
| `SEARCH_CACHE_TTL_SEC` | нет | 21600 | TTL кэша поиска |
| `SEARCH_CACHE_MAX` | нет | 2000 | записей в кэше поиска |
| `USAGE_LOG_PATH` | нет | `/logs/usage.jsonl` | путь к логу запросов и выборов (id хешируется) |
| `LOG_TTL_DAYS` | нет | - | срок хранения событий в SQLite, дней |

## Запуск (Docker)

```bash
docker compose up -d --build
docker compose logs -f
```

## Деплой на VPS

В `deploy.sh` укажите `VPS=user@host`, затем:

```bash
./deploy.sh
```

Скрипт синхронизирует код по ssh, соберёт образ и перезапустит контейнер.

npm run build && npm start

## Архитектура

- `bot.ts` - обработчики grammY на long polling, неблокирующие: дорогая работа уходит в фон, очередь апдейтов не копится. Здесь же логика стриминга: события прогресса сводятся в тексты статусов с throttle, чтобы не спамить чат.
- `search/orchestrator.ts` - ядро поиска: кэш → разбор LLM → объединение LLM-пула и split-перебора → детерминированный ранг → топ-N. Ранжирование по совпадению названия и автора, с fuzzy-матчем опечаток по Левенштейну; при равной оценке выше более популярное издание.
- `search/llm.ts` - LLM-клиент (OpenAI-совместимый) с единственным методом `parseQuery`.
- `search/flibusta.ts` - обёртка над npm-пакетом `flibusta`: OPDS-поиск, пагинация библиографии автора (плодовитые авторы не умещаются в первую страницу), выбор автора из тезок по популярности, таймаут на каждый сетевой вызов.
- `download.ts` - скачивание во tmpfs и распаковка zip-обёртки.
- `status.ts` - тексты статус-сообщений: фазы поиска, прогресс скачивания.
- `usage-log.ts` - лог запросов и выбранных книг в JSONL (telegram id хешируется sha256, содержимое не хранится).
- `db.ts` и `analytics.ts` - журнал событий в SQLite и дневные лимиты.

## Правовые аспекты

У книг на Flibusta разный статус авторских прав в зависимости от юрисдикции. Убедитесь, что имеете право скачивать контент в вашей. LLM-провайдер и модель настраиваются, поэтому соблюдайте условия использования выбранного провайдера.
